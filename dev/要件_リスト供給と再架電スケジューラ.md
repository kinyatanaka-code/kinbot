# 要件定義：リスト供給エンジン ＋ 再架電スケジューラ（＋リサイクル復活ルール）

作成：2026-09-06 / 対象：kincall（架電）
ステータス：**設計フェーズ**。復活ルールの「設定マスタ」だけ実装済み（`recycle_rules` テーブル＋設定・管理の編集UI）。実際の再浮上ロジックは未実装。

---

## 0. 全体像（1本のループ）

```
[リスト供給エンジン①]                 [再架電スケジューラ②]
  企業レコード                           不在・断りで記録
   ├ スコア（掲載中/業種/規模/履歴）      ├ 復活ルール(recycle_rules)を引く
   ├ 除外フラグ（死番/受付ブロック）      ├ next_call_at を決める（日数 or 指定日）
   └ 毎朝リスト生成（スコア降順）         └ 推奨時間帯・担当・トーク軸を付ける
        │                                     │
        ▼                                     ▼
   本日の架電リスト  ◀──「予約時刻が来たら上位へ自動再浮上」──┘
        │
        ▼
     架電 → 結果記録 →（不在/断りなら②へ戻る／獲得や明確拒否なら卒業）
```

①と②は **同じ企業レコード（`call_targets`）と架電ログ（`call_logs`）を共有** する。よってデータモデルを先に固める。

方針（変えない）：
- **同じ担当・同じ時間・同じトークで掛け直しても結果は変わらない。** 再架電時は「前回の断り理由・担当・時刻」を必ず表示し、どれかを変えて当て直させる。
- **温度A（押せば取れそう）** は断り理由タグに関わらず最優先で短期復活。ここが最も取りこぼしている層。
- **勝手に自動で挙動を変えない。** スコアの重みや復活日数は管理画面で人が調整でき、自動除外は「N回連続」等の閾値＋手動解除を残す。

---

## 1. データモデル

### 1.1 既存で使えるもの（追加不要）
`call_targets`（架電先＝企業レコード）
- `company / person / phone / email / industry / area / memo / assigned_to / owner_name`
- `stage / status`（SFステージ・状態）
- `next_call_at TIMESTAMPTZ` … **再架電予定日時（既存）**。②はここを使う。
- `extra JSONB` … 拡張置き場（下記の追加項目はまず extra に持たせ、効くと分かったら列に昇格でも可）
- `done / sort_order / created_at`

`call_logs`（架電ログ）
- `target_id / company / result / memo / caller / at / zoom_call_id / sf_task_id`
- `result` に架電結果（不在・アポ・断り 等）、`memo` に自由記述。

`recycle_rules`（実装済みの復活ルール設定マスタ）
- `tag`（断り理由タグ）/ `temperature`(A/B/C/卒業/連携) / `revive_weeks_min` / `revive_weeks_max` / `revive_note` / `trigger_note` / `next_owner` / `time_slot` / `talk_axis` / `graduation` / `sort_order`
- 設定・管理で編集可（クローザー・管理者）。GET `/api/calls/recycle-rules` / PUT `/api/calls/recycle-rules/:id`。

### 1.2 追加する項目

`call_targets` に追加（まず `extra` でも可、列にするなら以下）
| 列 | 型 | 用途 |
|---|---|---|
| `posted_media` | TEXT | 掲載媒体（doda・エン 等） |
| `posted_active` | BOOLEAN | 掲載中フラグ（顕在ニーズ＝最重要加点） |
| `emp_size` | INT | 従業員数（300〜999に加点） |
| `score` | INT | スコア（毎朝再計算・降順で上位へ） |
| `score_breakdown` | JSONB | スコア内訳（掲載中/業種/規模/履歴の寄与） |
| `excluded` | BOOLEAN | 恒久除外フラグ |
| `excluded_reason` | TEXT | 除外理由（死番＝現在使われていない／受付ブロック／候補者専用番号 等） |
| `block_reception` | BOOLEAN | 受付ブロック（常時）＝死番とは別扱い |
| `consecutive_absent` | INT | 連続不通回数（自動除外の閾値判定用） |
| `reject_tag` | TEXT | 直近の断り理由タグ（`recycle_rules.tag` と対応） |
| `temperature` | TEXT | 現在の温度（A/B/C/卒業/連携。メモから昇格も反映） |
| `recall_count` | INT | 再架電回数 |
| `partner_route` | BOOLEAN | 担当ルート/既存取引＝“社内連携”フラグ（リサイクルでなく連携で管理） |

`call_logs` に追加（再架電の意思決定を記録）
| 列 | 型 | 用途 |
|---|---|---|
| `recall_at` | TIMESTAMPTZ | この記録から決めた再架電予定日時 |
| `recall_reason` | TEXT | 再架電理由（戻り時間指定・週明け・◯月再検討 等） |
| `reject_tag` | TEXT | この架電の断り理由タグ |
| `time_bucket` | TEXT | 架電した時間帯（15時台 等。時間帯サジェスト集計用） |

※ **マイグレーションは `ADD COLUMN IF NOT EXISTS`** で。既存の架電フローを壊さないよう、まず列追加のみを入れて動作確認 → 次にロジック。

## 2. ① リスト供給エンジン

### 2.1 スコアリング（毎朝バッチ＋オンデマンド再計算）
擬似コード：
```
score(target):
  s = 0
  if target.posted_active:            s += W.posted        # 掲載中＝最重要
  if target.industry in HIT_INDUSTRIES(医療/福祉/製造): s += W.hit_industry
  if target.industry in MISS_INDUSTRIES(小売/サービス):  s -= W.miss_industry
  if 300 <= target.emp_size <= 999:   s += W.emp_size
  if 直近で断られた(reject_tag直近):   s -= W.recent_reject
  if 連続不通(consecutive_absent>=k):  s -= W.absent
  return s
```
- 重み `W.*` は **管理画面で調整可**（設定マスタ or settings）。実データで効き目を見ながらチューニング。
- 毎朝、担当ごとに `excluded=false && block_reception=false` を score 降順で並べ、「本日の架電リスト」を生成。

### 2.2 除外ロジック
- 「現在使われていない」を記録 → `excluded=true, excluded_reason='死番'`（恒久）。
- 「受付ブロック（常時）」→ `block_reception=true`（死番とは別。抑制はするが死番集計に混ぜない）。
- **誤操作対策**：1回で永久除外にしない。`consecutive_absent >= N（既定3）` で自動除外。手動解除の導線を残す。
- 「候補者専用番号」等は `excluded_reason` を区別して持つ（不通とは別扱い＝ケア21の例）。

### 2.3 画面
- 担当ごとの「本日の架電リスト」をスコア順。各行に **掲載中バッジ・業種・スコア**。
- 管理者向け：**「どのリスト元が死番を多く産んでいるか」** の集計ビュー（list_id × excluded_reason 件数）。

## 3. ② 再架電スケジューラ

### 3.1 復活ルールの適用（recycle_rules を参照）
不在／断りで記録するとき：
```
apply_recycle(target, log):
  tag = log.reject_tag
  rule = recycle_rules[tag]
  # 温度Aの昇格：メモに「押せば取れそう/優しい担当」等 → tag に関わらず温度A
  if memo_hits_hot(log.memo): target.temperature = 'A'; rule = recycle_rules['押せば取れそう（メモ付き）']
  else: target.temperature = rule.temperature

  # 復活日時
  if rule.trigger は「指定日/指定月」 and log に指定あり:
      target.next_call_at = 指定日時
  elif rule に週レンジあり:
      target.next_call_at = now + weeks(rule.revive_weeks_min..max の中央/下限)
  elif rule.temperature == '卒業' or rule.revive_note == '復活なし':
      archive(target)              # リサイクル卒業→アーカイブ
  elif rule.temperature == '連携' or target.partner_route:
      set_partner_route(target)    # 社内連携フラグ（リサイクルでなく連携）

  target.recall_count += 1
  log.recall_at = target.next_call_at
  log.recall_reason = 入力 or ルール既定
```
- **卒業／アーカイブ条件**（`recycle_rules.graduation`）を回数で判定：例「3回連続で充足→アーカイブ」「2回先送り→温度Cへ降格」「明確拒否→即アーカイブ」。判定には `recall_count` と直近の `reject_tag` 履歴を使う。

### 3.2 時間帯サジェスト
- `call_logs` の「result × 時間帯(time_bucket)」を会社・業種ごとに集計 → 繋がりやすい時間を算出。
- 既定は **接触率が高い15〜16時**（田中さんの分析）。17時台のような「退社済み」が多い時間は新規から外し、再架電・事務に回す。
- 既存の時間帯別接触率の分析ロジックがあるので、それをオンライン集計に載せる。

### 3.3 復活トリガーの実行（バッチ）
- 毎朝：`next_call_at <= 今日` の target を「本日の架電リスト」上位へ差し込み（ハイライト）。
- 「◯月に再検討」等の遠い先も、その月初に自動復活（`next_call_at` を該当月初に）。

### 3.4 画面
- 架電画面（既存の不在モーダル）に **「再架電予約」＝日時ピッカー＋理由入力**（不在モーダルは実装済みなので延長で速い）。
- 担当ダッシュボードに **「本日の再架電キュー」** を時刻順表示。予約時刻が来たらリスト先頭にハイライト。
- 再架電時は **前回の断り理由・担当・時刻を表示**し、「どれかを変える」を促すUI（担当/時間/トーク軸のいずれか変更を必須に近い形で）。

## 4. 実装順序（既存を壊さない小刻み）

1. **マイグレーション**：`call_targets`／`call_logs` に §1.2 の列を `ADD COLUMN IF NOT EXISTS` で追加（ロジックなし）。→ 既存フロー無変更を確認。
2. **除外ロジック**：既存の死番フラグ機能を拡張（excluded/excluded_reason/block_reception/consecutive_absent、自動除外の閾値と手動解除）。
3. **スコアリング**：score 計算＋重み調整UI＋「本日の架電リスト」をスコア順に。
4. **再架電予約**：不在モーダルに日時・理由。next_call_at 登録＋「本日の再架電キュー」。
5. **時間帯サジェスト**：result×time_bucket 集計、既定15〜16時、17時台を新規から外す。
6. **復活ルール適用**：recycle_rules を参照して next_call_at・温度・卒業を自動化（温度A昇格・卒業/アーカイブ・社内連携）。

①の除外と②の再架電予約は、すでにプロトタイプ済みの不在モーダル・死番フラグの延長なので着手が速い。②→効果（取りこぼし防止）が早く出る。①のスコア重みは②で運用データを貯めてから調整すると効く。
