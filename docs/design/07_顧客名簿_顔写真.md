## 1. 目的と範囲

**目的**：次の商談やCS引き継ぎの前に「誰が誰か」を顔で思い出せるようにする。担当者の交代や同席者の増加にも気づけるようにする。

**範囲に入れるもの**
- kinbot の Recall Bot が録画した商談（`meetings`、`mux_playback_id` あり）
- 顧客側の参加者ごとに顔写真を1枚切り抜き、企業と担当者に紐づける
- 企業ごとの名簿画面、担当者ごとの詳細（写真・役職・出た商談の一覧）

**範囲に入れないもの**
- 顔認識（顔の特徴量で同一人物を照合すること）。法的な扱いが重くなるため使わない（6章）
- 録画のない商談（MOCHICA 新規の商談は現状録画されていない）
- 社内メンバーの写真

## 2. 基本方針

1. **人と顔の紐づけは「Zoom の名前ラベル」と「話者の時刻」で行う。** 顔どうしの照合はしない。
2. **フレームは Mux のサムネイル API で取る。** `https://image.mux.com/{playback_id}/thumbnail.jpg?time={秒}` で任意時刻の静止画が取れるので、ffmpeg や動画のダウンロードは要らない。
3. **切り抜きは Gemini の画像入力で行う。** 既存の `gemini_failover.js` を使い、名前ラベルから参加者のタイルを見つけて顔の枠（bounding box）を返させる。
4. **自動で確定しない。** 名前の照合と写真の選択は「候補」として出し、営業担当が1クリックで確定する。失敗は黙らせず、理由を画面に出す。
5. **SF が担当者の正本。** 名簿の担当者は SF の Contact に紐づける。kinbot が持つのは写真と紐づけだけ。

## 3. 処理の流れ

```
商談終了（録画・文字起こし完了）
  │
  ├─①参加者の抽出   transcript の話者名 + Recall の participant 情報
  │                 → 社内メンバー（users / mcpeople / rep_name）を除外 → 顧客参加者
  │
  ├─②時刻の選定     顧客参加者ごとに「本人が話している時刻」を3〜5点選ぶ
  │                 （発話の途中・2秒以上続く区間の中央。冒頭1分と画面共有中は避ける）
  │
  ├─③フレーム取得   Mux サムネイル API で各時刻の静止画を取得（幅1280）
  │
  ├─④顔の切り抜き   Gemini に「静止画 + 参加者名」を渡し、JSONで返させる
  │                 { found, camera_on, label_text, face_box:[y0,x0,y1,x1], quality }
  │                 → 名前ラベルが一致し、カメラがオンのタイルだけ採用
  │                 → 枠を1.4倍に広げて正方形で切り抜き、256×256 に縮小
  │
  ├─⑤ベスト選択     quality（正面・ピント・明るさ）が最も高い1枚を代表写真に
  │
  ├─⑥担当者の照合   meetings.account → SF Account → listAccountContacts()
  │                 参加者名を正規化して Contact 名と照合（姓一致・全角半角・ローマ字）
  │                 一致1件=候補あり / 0件=「新規担当者」候補 / 複数=要選択
  │
  └─⑦確認と確定     商談詳細の「参加者」欄に候補を表示 → 営業が確定
                    未登録なら createContact() で SF に作成してから紐づけ
```

**実行タイミング**：既存の録画処理（Mux 登録・文字起こし）が終わった後、`scheduler.js` のジョブとして1商談ずつ非同期で実行する。過去分はバックフィル用のジョブで少しずつ処理する。

### 3.1 名前ラベルで決めきれない場合

| 状況 | 扱い |
|---|---|
| カメラオフ | 写真なしで参加者だけ登録。「カメラオフ」と表示 |
| 名前ラベルが「iPhone」「会議室」など | 話者名が取れれば話者の時刻で判定。1つの端末に複数人が映る場合は自動にせず「要選択」 |
| 話者が同時に複数 | その時刻は捨てる |
| 録画レイアウトがスピーカービュー | 名前ラベル照合の代わりに「話している本人が大きく映る」前提で判定（精度は下がるので quality を厳しく） |

※ 精度を上げたい場合は、Recall の録画設定に参加者ごとの個別映像（separate video）を追加すれば、タイル探しが不要になる。料金と保存量が増えるので、まずは合成映像で始める。

## 4. データモデル

```sql
-- 顧客側の人（SF Contact と 1:1 で紐づく。未確定のあいだは contact_id NULL）
CREATE TABLE customer_people (
  id            BIGSERIAL PRIMARY KEY,
  account_key   TEXT NOT NULL,          -- accounts.key
  sf_account_id TEXT,
  sf_contact_id TEXT UNIQUE,            -- 確定後に入る
  display_name  TEXT NOT NULL,          -- 録画上の表示名
  title         TEXT,                   -- SF の役職を写す
  photo_id      BIGINT,                 -- 代表写真（customer_photos.id）
  status        TEXT NOT NULL DEFAULT 'candidate', -- candidate / confirmed / rejected
  confirmed_by  TEXT,
  confirmed_at  TIMESTAMPTZ,
  created_at    TIMESTAMPTZ DEFAULT now(),
  updated_at    TIMESTAMPTZ DEFAULT now()
);

-- 商談ごとの出席（誰がどの商談に出たか）
CREATE TABLE meeting_attendees (
  bot_id        TEXT REFERENCES meetings(bot_id) ON DELETE CASCADE,
  person_id     BIGINT REFERENCES customer_people(id) ON DELETE CASCADE,
  speaker_name  TEXT,                   -- 録画上の名前（ゆれの記録）
  talk_sec      INT,                    -- 発話秒数
  camera_on     BOOLEAN,
  PRIMARY KEY (bot_id, person_id)
);

-- 切り抜いた写真（画像本体は Google Drive の限定フォルダ）
CREATE TABLE customer_photos (
  id            BIGSERIAL PRIMARY KEY,
  person_id     BIGINT REFERENCES customer_people(id) ON DELETE CASCADE,
  bot_id        TEXT,
  at_sec        NUMERIC,                -- 録画内の時刻
  drive_file_id TEXT NOT NULL,
  quality       NUMERIC,
  created_at    TIMESTAMPTZ DEFAULT now()
);

-- 処理の状態（黙った失敗を作らない）
CREATE TABLE face_jobs (
  bot_id        TEXT PRIMARY KEY,
  state         TEXT NOT NULL,          -- queued / running / done / failed / skipped
  reason        TEXT,                   -- 失敗・スキップの理由（画面に出す）
  frames_tried  INT, faces_found INT,
  updated_at    TIMESTAMPTZ DEFAULT now()
);
```

- 写真は1人につき代表1枚＋予備2枚まで残し、それ以上は捨てる。
- 画像本体を DB に入れず Drive に置くのは、既存の録画保存（`drive_file_id`）と同じ運用にそろえるため。配信は kinbot 経由（認証付きのプロキシ）で行い、Drive の共有リンクは発行しない。

## 5. 画面とAPI

### 5.1 画面
| 画面 | 内容 |
|---|---|
| 商談詳細 › 参加者欄（追加） | 顧客参加者の顔写真・名前・照合候補。「この人で確定」「別の人」「SFに新規作成」「写真を変える」 |
| 企業ページ › 名簿タブ（追加） | 担当者カード（写真・氏名・役職・初回登場日・最終登場日・出席回数）。最終登場が古い人は薄く表示 |
| 商談前ブリーフ（既存 `buildBrief`）への追加 | 今日の商談相手の企業の名簿を上に出す |

### 5.2 API
| メソッド | パス | 用途 |
|---|---|---|
| GET | `/api/accounts/:key/people` | 企業の名簿 |
| GET | `/api/meetings/:botId/attendees` | 商談の参加者と候補・処理状態 |
| POST | `/api/attendees/:personId/confirm` | 照合の確定（`sf_contact_id` 指定 or 新規作成） |
| POST | `/api/attendees/:personId/photo` | 代表写真の差し替え（予備から選ぶ） |
| DELETE | `/api/people/:personId/photo` | 写真の削除（本人から求められた場合など） |
| GET | `/api/photos/:id` | 画像の配信（ログイン必須） |
| POST | `/api/meetings/:botId/faces/rerun` | 再処理 |

## 6. 個人情報の扱い（実装前に法務確認が必要）

顔写真は個人情報（個人情報保護法）にあたる。次を前提条件とする。

1. **利用目的の公表**：「商談録画から取引先担当者の写真を作り、顧客管理に使う」ことをプライバシーポリシー等で公表する。録画の同意取得（Bot入室時の案内）に名簿化の目的も含める。
2. **顔認識はしない**：顔の特徴量（個人識別符号にあたる）は作らない・保存しない。紐づけは名前と時刻だけで行う。
3. **見られる人を限る**：その企業の担当営業・同じチーム・管理者のみ。外部AI連携（MCP / GPT Actions）からは画像を返さない。
4. **消せる**：担当者単位・企業単位で写真を消せる。本人から求められたら即時に消す。
5. **保存期間**：最終登場から2年で写真を自動削除（期間は法務と決める）。
6. **SF には写真を送らない**：SF の閲覧権限は広いため、写真は kinbot 内だけに置く。
7. **機能スイッチ**：`settings` に ON/OFF を持ち、企業単位で「名簿化しない」を指定できるようにする。

## 7. 失敗の扱い

| 失敗 | 対応 |
|---|---|
| Mux の静止画が取れない | `face_jobs.failed`、理由を参加者欄に表示。再処理ボタン |
| Gemini が失敗・形式不正 | `gemini_failover` で再試行。だめなら failed |
| 顔が見つからない（全員カメラオフ等） | `skipped`、理由「カメラオフ」 |
| SF に Account が無い／紐づかない | 写真だけ保存し「企業未確定」で表示 |
| 照合が複数一致 | 自動確定しない。候補を並べる |

処理件数・成功率・確定率は管理画面に出す（何件取れて何件止まったかが見える状態にする）。

## 8. コスト見積り（1商談あたり）

- Mux サムネイル：顧客3人 × 5枚 = 15回（追加料金なし）
- Gemini 画像入力：15回（Flash 系で十分。1回あたり数円以下）
- Drive 保存：1人 約20KB × 3枚
